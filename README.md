# SHISHO BINGO

Telegram bot and Mini App with a TiDB-backed wallet and Bingo rooms.

## Build and run

Use Node.js 20 or newer:

```powershell
npm install
npm run build
npm start
```

The build bundles `web/app.jsx` and its React dependencies into `public/mini-app.js`. Vercel runs this build command from `vercel.json`; keep the Vercel output directory unset so the Express app and its serverless routes remain active. Deploy again after changing the Mini App or backend.

Amharic number-call clips are served from `public/audio/amharic/`. To generate any missing clips, run `node scripts/generate-amharic-audio.js` with Node.js 20+ and an internet connection; the script uses Google Translate's unofficial text-to-speech endpoint.

Configure the existing bot, webhook, Telegram Mini App, TiDB, and `CRON_SECRET` environment variables in Vercel. Generate `CRON_SECRET` with `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"` and set the same value in local `.env` when running locally. Keep `.env` local and never commit it. The Hobby-compatible Vercel cron calls the protected `/api/cron/rooms` endpoint daily as a fallback. While a player is in a room, room-state polling and cartela actions process an expired countdown immediately; on Hobby, a room with no active clients may not be processed until the next daily cron. Upgrade to Vercel Pro and change the schedule in `vercel.json` to `* * * * *` if unattended countdown processing near the deadline is required. Open the Mini App using the SHISHO BINGO bot's native Play/menu button (or `/play`); a plain website URL has no signed Telegram launch data, so the server correctly withholds the user's wallet and does not allow joining. The wallet badge and bot balance command use the same available-balance calculation from the `wallets` table, including pending withdrawal reservations. The Mini App refreshes it on return to the foreground and every ten seconds while authenticated. The room/game tables are created by the existing database schema initializer.

## Rooms and game rules

When the lobby opens, the server automatically creates a persistent waiting room if no joinable room is available. The room list and room creation do not require identity data; joining, wallet access, and every game action still require verified Telegram Mini App authentication. This lets the lobby display its real room card even when the URL is opened outside Telegram, without allowing unauthenticated play. Lobby player counts are unique active room members, and the room card reports `SELECTING` when active cartela reservations exist, otherwise `WAITING` until play starts. The lobby refreshes room data every three seconds. A database row lock prevents simultaneous app opens from creating duplicate empty rooms. New rooms use a 30-second persisted cartela-selection countdown, a minimum of three valid active cartela reservations, a 20-player capacity, and cartelas cost 10.00 BIRR. Existing waiting rooms are migrated to the same three-cartela rule and get persisted countdown timestamps.

Each room has 100 generated cartelas; a player may hold up to two. JOIN authenticates the player, checks room status and capacity under a database row lock, then returns the current room/cartela state and authoritative available wallet balance. It also repairs missing or malformed unreserved cartela layouts in older rooms; layouts with an owner or active reservation are preserved rather than overwritten. Tapping an available cartela immediately updates the tile, displayed balance, selected count, and net pot optimistically, then queues the authenticated `POST /api/rooms/:id/cartela` reservation/debit request; server errors restore the authoritative room and wallet state. Deselecting uses the same immediate feedback and atomically refunds the stake while the room is waiting. The selected cartelas' stable 5×5 previews appear below the grid. Room state is available at `GET /api/rooms/:id/state` and is polled every 1.5 seconds during selection and live play. During play, the compact master board and player's card (or spectator view) update from the same server-issued call list.

At the 30-second selection deadline, the room starts only if at least three valid active cartela reservations exist; otherwise, it remains open and starts a fresh 30-second selection window. The start transition is idempotent and is processed by room polling and the configured Vercel cron (daily fallback on Hobby, every minute on Pro). Returning to the lobby preserves waiting-room membership and reservations; explicitly leaving a waiting room refunds them. Cartelas cannot be changed or refunded after play starts. The lobby refreshes its room listing every eight seconds.

When a room starts, the server creates and persists a cryptographically shuffled order of all 75 numbers. Calls are scheduled against the shared database start timestamp, not the time an individual client happens to poll, so every player and spectator sees the same sequence. The interval defaults to four seconds and can be changed with `BINGO_CALL_INTERVAL_SECONDS` (1–3600). The live board supports automatic marking and manual daubing; manual mode accepts marks only for numbers already called. A visible line, diagonal, or four-corners pattern only enables the player's Bingo claim button; calls continue until a player submits a claim. The server validates ownership and the pattern against its authoritative called numbers, then opens a three-second claim window. Calls pause during this window so concurrent valid claims can be included. Transient room-state polling failures are logged and retried on the next tick without replacing the game view with an error banner. On settlement, 80% of the room pool is split equally by winning player (if one player has multiple winning cartelas, that player's share is divided among those cards); any indivisible remainder cent is assigned deterministically. The remaining 20% is retained as the house fee. A finished game shows the verified winners and winning card, then automatically transitions directly to the next waiting room's cartela selection after seven seconds when one is available. Late visitors can watch rooms in `PLAYING` or `FINISHED` state without being counted as active players or acquiring cartelas. A game with all 75 numbers called and no winning claim ends without a prize.

This implementation uses database-backed polling rather than WebSockets, so active Mini App clients must remain open for calls to advance.
